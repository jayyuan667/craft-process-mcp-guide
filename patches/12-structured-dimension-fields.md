# Patch 12: structured dimension fields for slots

Risk: medium. Adds fields and a validator; the display string can remain for compatibility.

## Symptom

A valid dimension is rejected as malformed. Observed: `Ø75 (0/−0.2)` — a nominal diameter with an upper deviation of 0 and a lower deviation of −0.2 — was rejected as a format error. Rephrasing it did not help; every attempt failed validation while the drawing value stayed the same.

## Root cause

The slot value is a single string. Validation has to parse engineering notation out of that string, and the parser recognises a narrow set of spellings. Any legitimate variant the parser does not know — a different separator, a full-width symbol, a unilateral tolerance written as `0/-0.2` — is indistinguishable from a wrong value.

The string is also the storage format, so precision and structure are lost at the point of entry. Downstream rules then re-derive nominal and deviations from text, which is where the turning rule in [patch 8](08-slot-value-authority.md) gets its inputs.

## Change

Give a dimensional slot structured fields, and treat the string as display only:

```json
{
  "slot_id": "outer_diameter:1",
  "nominal": 75.0,
  "upper_deviation": 0.0,
  "lower_deviation": -0.2,
  "unit": "mm",
  "position": "left end, outer surface",
  "view": "main view",
  "evidence": {"text": "Ø75 0/-0.2", "bbox": [412, 288, 468, 316]},
  "display": "Ø75 0/-0.2"
}
```

Validation rules:

`nominal` must be a number; deviations are numbers relative to nominal, not absolute limits. `unit` is explicit, defaulting only when the drawing states it. `display` is generated by the server from the structured fields, or supplied as a read-only mirror; it is never the parse source.

Keep string input as a compatibility path: parse it once, store the structured fields, and reject only when parsing is genuinely ambiguous — with an error that names the expected shape:

```json
{"error": "invalid_dimension", "field": "nominal", "received": "Ø75 (0/−0.2)",
 "expected": {"nominal": "number", "upper_deviation": "number", "lower_deviation": "number", "unit": "mm"}}
```

## Acceptance

- `Ø75 0/-0.2`, `Ø75 (0/−0.2)` and a structured payload with `nominal=75, upper=0, lower=-0.2` produce the same stored slot.
- The generated card carries nominal and deviations as separate values; report rendering derives from them.
- A genuinely invalid value (missing nominal, non-numeric deviation) is rejected with the expected-shape error above.
- Existing string-only clients keep working through the compatibility path.

## Why it matters beyond one value

A gate that rejects correct input teaches operators to distrust the gate. The cost is not the retry; it is that the next rejection — a real OCR error — gets waved through by someone who has learned that rejections are usually false.
