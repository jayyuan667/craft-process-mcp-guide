# craft-process 故障恢复

`craft-process-workbench` 出错时的排查与恢复。只管"已经出事了怎么办"，正常流程的步骤与判据在那边，不在这里重复。

## 先定位断点，再动任何东西

在错误的层重启会毁掉证据。按顺序探：

| 层 | 探针 | 健康信号 |
| --- | --- | --- |
| 到壳的网络 | 连 MCP 端口 | 连接被接受 |
| MCP 协议 | `initialize` | `200` + `mcp-session-id` |
| 工具发现 | `tools/list` | 17 个 `craft_*` |
| 壳 → 后端 | 只读工具或后端 `/health` | `200` JSON |
| 后端业务 | 直接打对应 REST 端点 | 预期载荷 |

**能 `initialize` 并列出工具，说明壳是好的**；此后报连接失败，断点在壳到后端那一跳，改客户端配置没有用。

## 接不上时先分清三件事

1. **配置写了但工具没出现**——工具清单不热加载，**新开会话**再看。这一步能解决绝大多数"配了没用"。
2. **`initialize` 通、`tools/list` 空**——壳活着但工具没挂上，查壳的 MCP 路由与版本。
3. **工具在、调用报连接失败**——壳到后端那一跳，改客户端配置没有用。

前两种都不必等修好：技能自带 `scripts/craft_flow.py`（仓库检出时用 `tools/craft_flow.py`），直接走 REST，流程照跑；先用 `doctor` 或 `health` 确认连的是目标后端。

## 症状速查

| 症状 | 原因 | 动作 |
| --- | --- | --- |
| 配置写好了但工具列表里没有 | 工具清单不热加载 | 新开会话；仍没有就核配置文件名与语法——Codex/opencode 的键名各版本有差异 |
| `initialize` 通但 `tools/list` 为空 | 壳活着、工具没挂上 | 查壳的路由与版本；急用就先走 CLI |
| 工具连不上，但握手正常，错误文本带 loopback 地址 | 壳配置 `127.0.0.1`/`localhost`，在壳的命名空间里解析；容器里那就是容器自己 | 改成壳可达的地址（常见是容器网桥网关），**重建**容器——`restart` 不重读 env |
| MCP 端口上 `/health` 404 | 不是每个构建都暴露该路由 | 用 `initialize` 判活，后端单独探它自己的 health |
| 配成 5199 的 `/mcp`，返回 Flask 风格 404 | 那是后端，不是壳；本部署壳在 8764 | 改配 `:8764/mcp`，发 `initialize` 验 `200` + `mcp-session-id`；不要扫端口 |
| 工具报「文件不存在」 | 路径在壳所在主机解析，跨主机不传输字节 | 把文件放到壳能读的位置，或 multipart 直传后端 |
| 写操作返回 409 | revision 过期 | 重读工作台，把意图应用到当前对象上，带新 revision 写。**不要循环重发同一载荷**——revision 一直变说明有另一个客户端在写，停下来对账 |
| 有候选，generate 仍 409 | 候选 ≠ 已选 | 先 `template-selection` |
| 匹配 0 个候选，`before_count` 也是 0 | 没有模板进池（库空，或没有这个件的模板） | 停；问部署方该件有无模板，别改特征反复试探 |
| 分支条件都选了，仍卡在 `confirm_features` | 分支条件必须和 `features` 一起走 `feature-presence` | 重读工作台，三项一起提交，`features` 用列表 |
| 选模板超时或连接错误 | 同步长事务，可能超 60s；服务端可能在客户端放弃后才提交 | 先读工作台：已选就继续，不要重选；没选再带更长超时重试一次 |
| 导出成功但没有文件 | 产物写进了壳的容器 | 直连后端导出端点取响应体 |
| 复核后特征表塌了、值消失、计数倒退 | 发了最小载荷，端点整表替换 | 见下节「特征表被冲掉」 |
| 摘要干净但详细校验 partial | 摘要与详细校验不同源 | 四字段一起读，重读一次，仍矛盾就停下报告 |
| 合法公差被反复判格式无效 | 槽位只有字符串，校验器从显示文本解析 | 一次有依据的提交后停下，把原文/提交值/错误一起转交。**不要猜格式** |
| 改卡后 0 工时的工序变成空白 | `工时` 传了数字 `0`，被当成空值 | 全部转字符串重提交，导出与改前逐行比对 |
| 卡里的公差与确认值不一致 | 派生规则在生成阶段重算 | 用 `process-card-edit` 改回，不要重跑复核 |
| 工作台返回的是另一个任务 | 部署把状态放进程内存，多 worker 落到了别的 worker | **写之前停下**；每次写后比对 `job_id` |
| 上传超时、没有 `job_id` | 客户端先放弃，但任务可能已建 | 见下节「上传状态未知」 |
| 复核分析明显变慢，单项核对花了几分钟 | 在重做服务端已完成的提取与换算 | 停手：只做 20–30 秒矛盾扫视，最多切 1–2 张图；返回体里已有字段的直接用 |

## 恢复后从哪继续

修好之后不要从头重跑，回 `craft-process-workbench` 对应小节：

| 处理的是 | 回到 |
| --- | --- |
| 地址 / MCP 接入 | §0 先确认接没接上 |
| 上传丢了 `job_id` | §1，重传拿到新 id |
| 特征表被冲掉 | §4 复核（用保存的完整表重发） |
| 409 / revision | §3 读工作台，再回原步骤 |
| 模板匹配 / 选择超时 | §6 |
| 槽位与公差 | §7 |
| 导出 / 改卡 | §8 |

## 上传状态未知

`GET /api/jobs` 是 `405`，没有列表接口，不能靠 API 找回。顺序：

1. 看账本 `~/.config/craft-process/jobs.jsonl`，确认这次有没有 `attempt` 记录
2. 有 attempt 无 result → 按 sha256 / 文件名 / 时间对账，确认没建出来
3. 确认没有再 `--force` 重传，并说明「可能多一个孤儿任务，不影响已有结果」

**不要把「请人去工作台看看」当成唯一出路**——账本里有记录。但也不要因为怕重复建任务就把流程停死：`queued`/`running` 期间重复 create 才是浪费，对账后的重传不是。

四种事件：`attempt`（发字节前）、`result`、`timeout`（状态未知）、`failed`（被拒或连不上）。

## 特征表被冲掉

现象：提交复核后 `status` 变 unresolved、`value` 消失、`counts` 倒退。原因只有一个：载荷里只有 id 和 decision，而端点是整表替换。

恢复（有副本时）：提交前保存过完整 workbench 的话，把原始特征对象整体回传，同时带 `status`（confirmed/rejected）。原始尺寸候选还能从 `extraction.drawing_feature_fusion.structured_candidates` 取回。没有副本就只能重新识别。

预防：**写之前先存一份 full workbench**；`value` 一律转字符串；整个数组回传。

## 派生值覆盖了确认值

现象：正式卡里某处公差和你确认的不一致——确认了 `-0.05/-0.10`，卡里回来 `-0.05/-0.13`。

原因：派生规则在生成阶段重新计算，人工确认没有最高优先级。

处理：用 `craft_edit_process_card` 整体替换 `operations` 改回。**不要用「重跑复核」来修**——规则在生成时会再算一次，还是会被覆盖。

改卡前先存一份当前 `operations`；提交时把 `工时` 转成字符串（数字 `0` 会被当成空值）；改完导出，与改前逐行比对，不要只看返回 200。

## 状态矛盾怎么判

出卡前四字段：`replacement.validation.status`、`unresolved_slots`、`blocking_action`、`process_card`。四个必须互相印证。

矛盾的处理只有两步：重读一次工作台；仍矛盾就停下报告，把四个字段原样列出，**不生成、不导出**。不要用"摘要看起来可以"当放行依据——`counts` 会把 rejected 算进 unresolved，也可能在详细校验没过时看起来干净。

## 什么时候停

以下是正确结果，不是流程失败：

- 409 重读后同一个 revision 仍失败
- 公差有依据地提交一次后仍被拒
- 摘要与详细校验矛盾，重读一次仍矛盾
- 工作台返回的 `job_id` 不是你要的那个
- 找不到后端地址
- 匹配 0 候选且 `before_count == 0`，部署方还没确认这个件有没有模板

停下时把证据原样列出：请求、返回、revision、时间点。不要替用户"猜一个合理的值"继续往下走。

## 不要做

- 不要重做服务端已给出的提取、换算或模板判断（见 workbench 的「分工」一节）
- 不要在错误的层重启（会毁证据）
- 不要循环重发同一载荷
- 不要扫端口找地址（详见仓库 docs/08）
- 不要用另一个 job 的确认结果替代本次确认
- 不要把失败当成功继续往下走
