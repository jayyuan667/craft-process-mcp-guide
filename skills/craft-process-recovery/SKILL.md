# craft-process 故障恢复

**边界**：这里只回答两件事——断在哪一层、回到 `craft-process-workbench` 的哪一节。每一步怎么做不在这里重复。

## 0. 先拿三样证据（10 秒）

```bash
python scripts/craft_flow.py doctor
```

把它的四行输出（地址 / 后端 / 任务 / 下一步）连同下面两样一起看：

- 最近一次请求和它的返回原文（含 `revision`）
- 工作台返回里的 `job_id`

没有这三样就不要开始改任何东西。**在错误的层重启会毁掉证据。**

## 1. 断点表

按顺序探，第一个不健康的就是断点层：

| 层 | 探针 | 健康信号 |
| --- | --- | --- |
| 到壳的网络 | 连 MCP 端口 | 连接被接受 |
| MCP 协议 | `initialize` | `200` + `mcp-session-id` |
| 工具发现 | `tools/list` | 17 个 `craft_*` |
| 壳 → 后端 | 只读工具或后端 `/health` | `200` JSON |
| 后端业务 | 直接打对应 REST 端点 | 预期载荷 |

**能 `initialize` 并列出工具，说明壳是好的**；此后报连接失败，断点在壳到后端那一跳，改客户端配置没有用。

## 2. 症状 → 判定 → 动作 → 回到

| 症状 | 判定 | 动作 | 回到 |
| --- | --- | --- | --- |
| 配置写好了但工具列表里没有 | 工具清单不热加载 | 新开会话；仍没有就核配置语法（Codex/opencode 键名各版本不同） | §0 |
| `initialize` 通但 `tools/list` 为空 | 壳活着、工具没挂上 | 查壳的路由与版本；急用先走 CLI | §0 |
| 工具连不上，错误文本带 loopback | 壳配了 `127.0.0.1`，在壳的命名空间里解析 | 改成壳可达地址，**重建**容器（`restart` 不重读 env） | §0 |
| MCP 端口上 `/health` 404 | 不是每个构建都暴露该路由 | 用 `initialize` 判活，后端单独探 | §0 |
| 配成 5199 的 `/mcp`，得到 Flask 风格 404 | 后端端口，不是壳 | 改配 `:8764/mcp`，验 `200` + `mcp-session-id` | §0 |
| 工具报「文件不存在」 | 路径在壳所在主机解析 | 文件放到壳能读的位置，或 multipart 直传后端 | §1 |
| 写操作 409 | revision 过期 | 重读工作台，把意图应用到当前对象，带新 revision 写；**不要循环重发同一载荷** | §3 |
| 有候选，generate 仍 409 | 候选 ≠ 已选 | 先 `template-selection` | §6 |
| 匹配 0 候选，`before_count` 也是 0 | 没有模板进池（库空或没有这个件的模板） | 停；问部署方该件有无模板，别改特征试探 | 停 |
| 分支条件选了，仍卡 `confirm_features` | 分支条件必须与 `features` 同提交 | 重读工作台，三项一起提交，`features` 用列表 | §5 |
| 选模板超时或连接错误 | 同步长事务，服务端可能在客户端放弃后提交 | 先读工作台：已选就继续；没选再带长超时重试一次 | §6 |
| 导出成功但没有文件 | 产物写进壳的容器 | 直连后端导出端点取响应体 | §8 |
| 复核后特征表塌了、计数倒退 | 发了最小载荷，端点整表替换 | 见下节「特征表被冲掉」 | §4 |
| 摘要干净但详细校验 `partial` | 两个信号不同源 | 四字段一起读，重读一次；仍矛盾就停 | §8 |
| 合法公差被判格式无效 | 槽位只有字符串，校验器从显示文本解析 | 一次有依据的提交后停，把原文/提交值/错误一起转交；**不要猜格式** | 停 |
| 改卡后 0 工时工序变空白 | `工时` 传了数字 `0` | 全部转字符串重提交，导出与改前逐行比对 | §8 |
| 卡里公差 ≠ 确认值 | 派生规则在生成阶段重算 | 用 `process-card-edit` 改回；**不要重跑复核** | §8 |
| 工作台返回的是另一个任务 | 多 worker 状态落错 | **写之前停下**；每次写后比对 `job_id` | 停 |
| 上传超时、没有 `job_id` | 客户端先放弃，任务可能已建 | 见下节「上传状态未知」 | §1 |
| 复核明显变慢，单项核对花几分钟 | 在重做服务端的提取与换算 | 停手，只做矛盾扫视 | workbench「分工」 |

「回到」是 workbench 的小节号；写「停」表示这一步没有可继续的动作，交证据给人。

## 3. 三种没有现成步骤的恢复

这三件 workbench 不写，只在这里给最短路径。

**上传状态未知。** 账本 `~/.config/craft-process/jobs.jsonl` 里找这次有没有 `attempt`：有 attempt 无 result 就是状态未知，按 sha256/文件名/时间对账，确认没建出来再 `--force` 重传，并说明可能多一个孤儿任务。`GET /api/jobs` 是 405，没有别的找回路径。

**特征表被冲掉。** 有提交前的完整 workbench 副本就整体回传（原对象 + `status=confirmed/rejected`）；没有副本，尺寸候选还能从 `extraction.drawing_feature_fusion.structured_candidates` 取回；都没有就重新识别。

**派生值覆盖了确认值。** 卡里的公差和确认值不一致时，用 `process-card-edit` 改回。重跑复核会再算一次，等于没改。

## 4. 什么时候停

停是正确结果，不是流程失败：409 重读后仍失败、公差提交一次仍被拒、摘要与详细校验重读后仍矛盾、`job_id` 对不上、找不到地址、0 候选且部署方未确认、壳与后端断在错误的层且无权限修。

停下时交这五样：`job_id`、当前 `revision`、断点层、请求与返回原文、回到哪一节或无解的原因。

## 5. 不要做

- 不要在错误的层重启（会毁证据）
- 不要循环重发同一载荷
- 不要扫端口找地址（仓库 `docs/08`）
- 不要用另一个 job 的确认结果替代本次确认
- 不要把失败当成功继续往下走
